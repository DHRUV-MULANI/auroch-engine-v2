# New dataset: scale-sensitivity results

Generated by `python scripts/scale_sensitivity.py --input data/lngraph_2021_11_27__21_00.json --output results/new_dataset`.

**This is a proxy experiment, not a faithful reproduction of the Auroch paper.**
See `raw/metadata.json` for the exact configuration and caveats.

## Why this bundle exists

The old root snapshot (`lngraph_2021_11_27__00_00.json`) has 18,310 nodes / 80,743
channels. The paper reports 18,331 nodes / 80,918 channels. The downloaded
hourly archive contains an **exact match**:

```
discharged-pc-data-master-snapshots/snapshots/lngraph_2021_11_27__21_00.json.zst
    -> 18,331 nodes, 80,918 channels
```

That snapshot was extracted to `data/lngraph_2021_11_27__21_00.json` and is the
input for every run here.

## Is the new dataset enough to see changes?

Yes for **snapshot fidelity**, limited for **snapshot variation**:

- The archive has 1,542 hourly graphs (2021-11-25 15:02 -> 2022-01-28 20:00).
- 129/129 snapshots from Nov 25-30 are near the paper's counts. Within this
  usable window topology barely moves: nodes 18,265-18,336 (0.4% spread),
  channels 80,362-81,018 (0.8%), total capacity 3,249-3,285 BTC (1.1%).
- Late snapshots degrade sharply (2021-12-12: 12,024 nodes / 39,346 channels;
  2022-01-28: 1,885 nodes / 3,839 channels) and are unusable as paper inputs.

So visible low-to-high differences in these plots come mainly from the
**capacity multiplier** and **workload length**, not from dataset size. The
exact-match snapshot fixes the count mismatch, but do not expect large
metric swings from choosing a different hour inside the stable window.

## Configuration

| Setting | Value |
|---|---|
| Input | `data/lngraph_2021_11_27__21_00.json` (18,331 / 80,918) |
| Transaction counts | 5,000 / 7,000 / 9,000 |
| Capacity scales | **1x / 2x / 3x / 4x / 5x / 6x / 7x / 10x** (dense low range) |
| Repetitions | 20 per setting |
| Simulations | 5 methods x 3 counts x 8 scales x 20 runs = **2,400** |
| Seed | 20261116 (`seed + run` per repetition) |
| OD pairs | 128 fixed source/destination pairs reused |
| Payment amounts | synthetic log-uniform 1,000-1,000,000 sat |
| Liquidity | 50:50 directional split, updated after successful payments |
| Fees | static proxies: 1 sat + seeded rate [0,10] x amount; dynamic Auroch: 1 sat + tau(liquidity) x amount |

The paper's 30x/50x/70x points are deliberately **omitted**: at those sizes the
curves saturate and the four methods overlap, so the difference cannot be seen.
The low range is sampled densely (including 3x/5x/7x) so curvature and method
separation are visible.

## Methods (all proxies)

Multipath proxies use **water-filling**: the payment is split across candidate
paths instead of draining the first path, so Auroch uses ~3-4 paths, Spider
~1-2, and single-path methods exactly 1. The earlier build drained the first
path, which made every proxy look like Dijkstra.

1. Auroch-inspired three-path multipath with water-filling (no auction / LP)
2. Auroch + dynamic liquidity fee: the proposed `tau_from_liquidity()` is
   **executed** — cached paths are re-ranked by current liquidity and each hop
   charges `1 + tau * amount`. This is a real algorithm change, not a plotted
   formula or edited numbers.
3. Modified Dijkstra single cheapest-path proxy
4. Spider-inspired four edge-disjoint paths with water-filling
5. SpeedyMurmurs-inspired three-landmark route (single path)

## Caveats

- Payment amounts are synthetic; the Bitcoin transaction-volume trace is not
  available locally. Ripple workload sizes are also unavailable.
- Channel policies are ignored; parallel channels are aggregated per directed
  endpoint pair.
- Capacities are scaled 3x-70x; balances are assumed 50:50.
- The four routing methods are labelled proxies. The real auction (RREQ/RREP,
  bidding rules, Equations 3-7) and ECDSA are not executed in this benchmark.
- The dynamic tau curve in `dynamic_tau_curve.png` shows the tau function; the
  `auroch_dynamic_proxy` series **does execute** that function per hop. It is
  still a proxy — the paper's auction/bidding protocol is not implemented.
- The 30x/50x/70x paper settings are not in this bundle; `final_results/` keeps
  the earlier six-scale run for reference.
- Routing time excludes route-cache construction, so it is not a paper metric.

# Success-ratio experiment (new)

Files: `success_experiment.json`, `success_per_run.csv`, `success_deciles.csv`,
`success_failures.csv`, `cached_routes.json`.
Generator: `python3 scripts/success_experiment.py --output data --workers 6`.

This experiment isolates why the old proxy sat near 0.2–0.5 and what raises it.
It uses the same exact snapshot, 5,000 payments per run, 3 runs, 50:50 initial
liquidity and seeded log-uniform 1,000–1,000,000 sat amounts. Three methods are
reported for scales 1/2/3/5/7/10/20/30/50/70:

- `cached3` — the old proxy: three shortest paths cached per OD pair and reused
  for the whole run. Workload `fixed128` (128 reused OD pairs).
- `flow` — an Eq7-style feasibility allocation: per-payment max-flow on the
  **current residual balances**, decomposed into paths. Edges are capped at the
  payment amount and a virtual source/sink keeps scipy's solver inside int32,
  which matters at 30–70x. This is a real routing change: routes are discovered
  against live liquidity instead of a frozen cache.
- `ceiling` — the same flow on untouched initial balances. No router can beat
  it, because the sender and receiver still have to fit the payment.

Two workloads are measured for `flow` and `ceiling`:

- `fixed128` — the original benchmark workload, 128 OD pairs reused ~39 times.
- `diverse` — one independently sampled OD pair per payment, the standard
  model when no real payment trace is available.

`success_ratio` means successful payments ÷ attempted payments;
`success_volume` means delivered satoshis ÷ attempted satoshis;
`deciles` mean the success ratio inside each tenth of the payment sequence.

The two fixes are reported separately on purpose. Live route discovery raises
success on the fixed workload, but the reused endpoints remain a workload cap.
Sampling diverse endpoints removes that cap and brings the measured ratio close
to the liquidity ceiling. Neither result is a paper reproduction: the auction,
bidding, policies and fees are not executed in this benchmark.
